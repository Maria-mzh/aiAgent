# App UI 产品原型设计

把模糊需求转化为可评审的产品方案和可直接预览的 `UI.html`。兼顾业务闭环、交互完整性、视觉一致性与前端可实现性。

## 工作流程

1. 读取用户需求、现有项目、品牌素材与约束。若上下文足够，直接执行；只在关键业务选择会显著改变方案且无法合理推断时提问。
2. 从产品经理视角梳理：目标用户、核心场景、用户目标、业务目标、范围边界、核心任务链路、功能优先级、规则、异常和空/加载/成功/失败等状态。
3. 建立信息架构：页面清单、导航模型、内容层级、页面间跳转和每页核心行动。避免为了展示而创建无业务价值的页面。
4. 先确定视觉系统，再实现页面。保持统一的间距、圆角、阴影、色彩、组件和交互反馈。
5. 从 `assets/mobile-ui-shell.html` 复制骨架并生成 `UI.html`；不要修改资产原件。单页任务至少生成一个手机画板，多页面流程按任务顺序横向排列。
6. 检查 HTML 结构、页面尺寸、内容溢出、导航一致性和关键状态。条件允许时在浏览器中渲染并截图检查；发现问题后迭代。
7. 向用户交付简洁的产品设计摘要、关键假设和 `UI.html`。用户若明确只要文件，则把必要设计说明写入 HTML 顶部注释。

## 产品拆解标准

输出足以支持产品、设计和研发评审的内容：

- 产品目标与成功标准：说明解决谁的什么问题，以及核心结果。
- 用户与场景：明确主要角色、触发条件、任务和期望结果。
- 功能设计：按 Must/Should/Could 排序；说明入口、前置条件、主流程、业务规则、反馈与边界。
- 信息架构：列出页面、一级/二级内容、全局导航及页面关系。
- 交互状态：覆盖默认、操作中、空、加载、成功、失败、禁用和权限不足；仅保留适用状态。
- 页面说明：逐页列出页面目的、内容模块、主要操作、次要操作和去向。
- 假设：把需求未明确但为完成设计所做的合理推断明确标注。

不要虚构复杂后端能力或额外业务范围。对敏感、支付、删除等高风险动作提供确认和可恢复反馈。

## 视觉与实现规范

- 使用优雅极简主义，柔和蓝色渐变、充分留白、轻盈通透的层次、微妙阴影、模块化卡片、精心圆角和克制微交互。
- 强调色使用蓝色；所有可见文字只能为纯黑或纯白。可用透明度形成次级层级，但不要使用灰色或其他彩色文字类。
- 每个手机画板固定 `w-[375px] h-[812px]`，带描边或深色边框模拟手机边框，并设置 `overflow-hidden`。
- 使用 Tailwind CSS CDN 完成主要样式；仅为玻璃效果、滚动条、关键帧等 Tailwind CDN 不便表达的内容写少量 CSS。
- 使用 Remix Icon 在线矢量图标。图标本身不得带背景色块、底板或外框；按钮容器可有符合交互语义的表面样式，但不要把图标画成徽章。
- 图片必须通过开源图片网站的 HTTPS 链接引入，添加准确 `alt`，使用 `object-cover`，并通过渐变或背景色保证加载失败时布局仍可理解。
- 保留安全区：顶部状态栏不遮挡内容，底部导航不遮挡滚动内容；页面内容通常从 `pt-12` 开始并为底栏预留至少 `pb-20`。
- 状态栏、底部导航和 Home Indicator 在同一套页面中保持一致；当前导航项清晰，非当前项使用黑色配合透明度，不使用灰字。
- 使用真实、简洁、贴合场景的中文文案，避免“标题”“描述”“功能”等占位词。
- 为按钮、卡片和导航添加 `cursor-pointer`、`hover`/`active`/`transition` 等轻量反馈；纯静态原型无需引入框架。
- 若用户提供品牌规范、技术栈或现有组件，优先遵循用户约束，并在不冲突处应用本技能风格。

## 验收清单

- `UI.html` 可独立打开，包含 Tailwind CDN 与 Remix Icon。
- 每个画板严格为 375×812，手机边框、状态栏和安全区正确。
- 页面覆盖核心任务链路，CTA、反馈、异常状态和跳转意图明确。
- 所有可见文字为黑色或白色，没有灰色/蓝色文字。
- 图标无自身底板；远程图片有开源链接与 `alt`。
- 不存在 TODO、无意义占位、被底栏遮挡的内容或明显横向溢出。
- 视觉层级、间距、圆角、阴影和导航在所有页面一致。
